# P2配送経路の運用改善・検証報告（2026年11月18日）

## 0. 対象と結論

本版は、保存済み `suita_delivery_support_P0_P1_swapped_20261113.zip` を基礎として、P2配送計画に伴う不自然な多数訪問・早期供給と完了時間の評価の扱いを修正した**検証版**である。オンラインに公開されているアプリの現行コードを取得・更新したものではない。

論文に従う基本式は保持する。段階名はアプリの方針に従って**P0＝理想配分、P1＝実行可能な配分・出動計画、P2＝経路計画**と表記する。論文の元の P0/P1 の表記と混同しないこと。

- **F₂**＝各配送回で最も帰着が遅い車両の所要時間を、全配送回で足したもの。積込・移動・施設準備・荷卸し・帰着を含む。1台ごとの走行時間の合計や「最初の施設への到着時間」ではない。
- **F₃**＝最終候補配送回を除く各配送回終了時における、各施設の目標未達度の重み付き合計。対象期間は候補最大回数に固定する。F₃が小さくても均等配分・一定時間内の初回到着は自動では保証されない。
- **トレードオフ**＝同じ最終配分を届けても、早い回に物資を届けるための寄り道・再訪問でF₂が悪化する場合がある。パレート候補の中から運用方針で選ぶ必要がある。

## 1. 変更した運用設定

### ① 1車両・1配送回の訪問施設数上限

- `maxStopsPerRoute` を追加。初期値 **8施設**、画面選択肢は 4／6／8／10／12／16施設（入力処理は1～40施設）。
- P1の車両・配送回の割当に上限を入れ、P2の経路改良・候補検査でも同じ上限を厳格に検証する。
- 訪問上限は**論文由来の決定値ではない追加の運用条件**。施設数100、車両台数、最大配送回数、最低配送量との組合せによっては実行不可能になる。この場合は上限を隠れて緩めず、実行不可能理由を返す。
- 代表配送地点に統合された施設も、受け渡し数量・配分評価は施設ごとに維持する。**施設訪問数**と**現地の物理停車地点数**は別々に出力する。

### ② F₂とF₃の同時評価

- `p2ExtraTimePercent` を追加。初期値 **10%**、画面選択肢 0／5／10／20／30%。
- まず作成・検証された実行可能候補の最小F₂を求め、その **F₂＋追加時間許容幅**の候補に限ってF₃を最小化する。F₃同点ならF₂、走行距離、再訪問などの順に比較する。
- これは政策判断のための **ε制約型の候補選択ルール**であり、論文が固定した必須の割合ではない。候補生成は局所探索を含むため**厳密なパレート前線・全体最適性は保証しない**。
- 早い配送回への物資一部分割候補を追加。最低配送量、車両積載量、各拠点在庫、訪問数、配送時間、最終配分のF1許容値を維持できた候補のみ採用する。

### ③ 初回到着の確認と任意期限

- `p2MaxFirstSupplyMinutes` を追加。**初期値は未指定**。指定すると全未訪問必須対象がその時間までに最初の物資を受け取れる候補だけを残す。
- 条件を満たす候補がない場合は計算不能として明示し、勝手に期限を延長しない。
- 回終了ごとのF₃とは別に、`firstSupplyArrivalMin` と `maxFirstSupplyArrivalMin` を出力する。
- 物資の実際の到着時刻の管理を強める**追加運用条件**であり、原論文のF₃数式とは別である。

### ④ 代表点の経路改善・確実性

- 同じ代表点の避難所を経路内で連続処理し、同じ代表点へ離れてから再訪問する順序を避ける。
- 少数代表点に限る動的計画法でその車両ルートの代表点訪問順序を比較。全車両・全配送回の厳密最適化ではない。
- 車両が拠点に戻るまでをF₂に算入し、全体累積時間、回ごとの上限、最低配送量と在庫・配分を再確認。
- Google交通情報が利用不可の場合は従来通り **マンハッタン距離÷20km/h**の推定値。**実道路規制や迂回を完全に反映した時間ではない**。

## 2. 検証結果

| 確認内容 | 結果 |
|---|---|
| 旧モデルからの回帰 | 8件とも通過 |
| 追加運用テスト | 4件とも通過。計12件の単体テストが成功 |
| 従来通過していた16施設/回・車両 | 上限8設定で拒否。上限16への変更で許可 |
| F₂/F₃優先順位の検算 | (F₂,F₃)=(80,9),(100,8),(120,8)で0/10%→前者、25/30%→中者。支配解を選ばない |
| 初回到着期限 | 1分という非実現条件は正しく拒否 |
| 100施設試験 | 100施設すべて訪問、1車両・1回最大8施設、時間・在庫条件を検証済み |
| 100施設→80代表点試験 | 20組の2施設と60単独施設で人工的に構成。100施設全部訪問、代表点の同一ルート内連続訪問を確認 |

**100施設・80地点の試験条件：**スイタ市配分データから必要データ100施設を読み出し、2t車両10台、最大5回、各拠点5台、最小13.5kg、1回360分・累積1080分、在庫1777キット（889/888に仮分割）、訪問上限8、追加時間10%。所要時間はマンハッタン距離÷20km/hの**計画上の仮定**。この試験でF₂は約**287.9分**、最大1回約**202.3分**、最大1車両あたり**8施設**、実際に使った配送回は2回。代表点80地点は**試験用の人工的な統合構成**であり、現在のWeb表示が自動生成する代表点80地点と同一であるとは主張しない。

## 3. 未完了の検証・留意事項

1. **実道路での最終妥当性の保証は未完了**。Google道路行列・実際の拠点進入路・片側通行・迂回・緊急交通路制約の確認が必要。
2. **全体最適性は未証明**。P1の整数計画で示す評価上界と、P2の経路探索で得られた候補を区別する。P2の候補数が少ないと、許容時間を増やしてもF₃改善を実現できない。
3. **モデルのF₃と「公平な同時配分」は異なる**。F₃は回単位の目標未達累積であり、特定の施設の最初の到着を直接最小化しない。必要に応じ初回到着期限を併用する。
4. **配送途中の車両運転・荷役安全を保証する制度的な基準ではない**。8施設/回は暫定的な運用選択であり、実地の運行規定・職員数・最大作業時間と突き合わせて決定する必要がある。
5. **画面とAPIの統合動作**の最終確認には、実稼働相当の環境（Google API設定、Webセッション、クラウド配備）が必要。実際のWebサービスへはデプロイしていない。

## 4. 実行方法

1. ZIPを展開し、`suita_delivery_support` をプロジェクトルートとして利用。
2. `pip install -r requirements.txt` を実行。
3. `python -m unittest discover -s tests -v` により12件のテストを実行。
4. `python app.py` でアプリを起動（環境変数・地図APIキーなどは既存設定に従う）。
5. P1画面で訪問上限を設定して計画し直し、P2画面で追加時間許容率と必要なら初回到着期限を入力して再計算。過去の保存済みP1/P2結果はアルゴリズム改訂番号84で無効化され、最新設定での再計算が必要。

**注意：**本書の数値は検証用の仮定に基づく計算例であり、実災害の所要時間・公式な配送可能性・最適性の証明ではない。

**実行環境に関する追加検証事項：** Pythonの各モジュールの構文検査、およびブラウザ用JavaScriptの静的構文検査は通過した。ただし、本検証コンテナには Flask がインストールされていないため `app.py` のHTTPリクエストを伴う統合試験は未実施。デプロイ前に `pip install -r requirements.txt` した環境で、P1→P2の一連の画面・API動作を実行確認すること。
